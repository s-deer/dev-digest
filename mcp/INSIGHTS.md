# mcp insights

Non-obvious lessons learned while working here — what was tried, what didn't
work, and why. One entry per insight (date + short title + a few lines),
newest last. Skip routine changes; only record what would otherwise get
re-discovered the hard way.

## What works

- **2026-09-27 — `Agent.array()` / `Repo.array()`, not `z.array(Agent)`, to parse a shared schema.** Calling the array method *on* a schema imported from `@devdigest/shared` (`Agent.array()`) keeps the whole expression on the schema's own zod instance. Wrapping it with mcp's own top-level `z.array(Agent)` (from `mcp/src/api/http.ts`) type-checked, but `tsc` silently widened `.default()` fields (`strategy`, `ci_fail_on`, `repo_intel`) back to optional in the inferred output type, breaking `Promise<Agent[]>`. Evidence: `mcp/src/api/http.ts`'s `listAgents`/`listRepos`.
- **2026-09-27 — Duck-typed `SafeParser<T>` instead of `z.ZodType<T>` in a generic parse helper.** A local `interface SafeParser<T> { safeParse(body: unknown): {success:true;data:T}|{success:false;error:unknown} }` avoids the same `.default()`-widening problem as above when a schema from `@devdigest/shared` flows through a generic function. Typing the same parameter as mcp's own `z.ZodType<T>` reintroduces it. See `mcp/src/api/http.ts#parse`.
- **2026-09-27 — `npm --prefix mcp run -s start` as the `.mcp.json` command.** `claude mcp list` (run from the repo root) parses `.mcp.json` and lists `devdigest` without a resolution error, and `npm --prefix mcp run -s start` run manually from the repo root does start the server (confirmed via a scripted stdio JSON-RPC session: `initialize` → `tools/list` → `tools/call`). I could not fully verify the actual spawn cwd Claude Code uses for a project-scoped stdio server without completing the interactive first-time approval prompt (`⏸ Pending approval`, not auto-approvable headlessly). `npm --prefix mcp run -s start` was chosen over a raw `mcp/node_modules/.bin/tsx --tsconfig mcp/tsconfig.json mcp/src/index.ts` invocation because it has one relative path to resolve instead of three, and it re-uses `package.json#scripts.start` as the single source of truth.

## Decisions

- **2026-09-27 — Tools register through a hand-written `registerTool()` wrapper (`src/tools/_register.ts`), not `McpServer.registerTool` directly.** `@modelcontextprotocol/sdk@1.30.1`'s `registerTool` is one heavily generic overload (`<OutputArgs, InputArgs>`); with `zod@3.25.76`, inferring both generics from a schema with an array-of-object field, or several chained modifiers (`.min().max().default().describe()`), intermittently makes `tsc` either report `TS2589: Type instantiation is excessively deep` or, on a full build, crash with a V8 heap OOM (`FATAL ERROR: ... JavaScript heap out of memory`, `tsc` had allocated the whole 4 GB default heap and kept growing). The failure was **not deterministic per call site**: the same `registerTool(...)` expression, copy-pasted into a throwaway file with a different tool name, type-checked fine in the *same* program (same `tsconfig.json`, same full file set) while the real call — differing only in being *invoked* from `server.ts` alongside a second `registerTool` call for a different tool — failed. Explicitly widening the schema variables (`: z.ZodTypeAny`, `: z.ZodRawShape`) and/or supplying explicit generic type arguments each fixed *some* reproductions but not the real files reliably. The robust fix: `_register.ts` exports a non-generic `registerTool(server, name, config, handler)` that casts `server.registerTool` to a small hand-written function type once. This makes every tool registration's type-checking cost constant instead of depending on unrelated files elsewhere in the compilation. Runtime behavior is unchanged — the SDK still validates input/output against the real zod schemas at call time; only `args`'s static type inside a handler is lost, so each handler casts `rawArgs` to its own local interface (e.g. `GetConventionsArgs`) before use. **Revisit if** a future SDK/zod pairing fixes the underlying inference bug — the wrapper is unnecessary once `server.registerTool(...)` can be called directly and type-checked in isolation *and* as part of the full program.
- **2026-09-27 — `list_agents`'s empty input schema is a real `z.object({}).strict()`, not a raw `{}` shape.** The SDK only emits `additionalProperties:false` when `inputSchema` is an actual constructed Zod object schema; an empty raw shape (`{}`) or an omitted `inputSchema` both render as `{type:"object", properties:{}}` with no `additionalProperties` key (verified by calling `client.listTools()` over an `InMemoryTransport` pair for all three variants). Since tool registration goes through the `_register.ts` wrapper (previous entry), passing a real `ZodObject` here no longer risks the `tsc` depth issue.
- **2026-09-27 — The 5000-char `tools/list` budget required dropping every tool `title` and field-level `.describe()`, not just shortening prose.** Benchmarked with `JSON.stringify(tools)` over an `InMemoryTransport` client: with the flag off (4 tools), the *structural* floor alone — every schema field, `annotations`, and the SDK's fixed `execution:{taskSupport:"forbidden"}` per tool, but zero description/title text anywhere — was already 4830 chars; the pre-trim code (full tool + field descriptions) measured 6209 chars. That left roughly 170 chars of budget for *all* prose combined once `title` was kept, not enough for even one short field hint per tool. Final state: no `title`, no field `.describe()`, one ≤50-char top-level `description` per tool; the "what to call next" flow now lives only in `createServer`'s `instructions` string. Measured 2026-09-27: 4953 chars (~1239 tokens at chars/4) with the flag off, 5485 chars (~1372 tokens) with `DEVDIGEST_MCP_ENABLE_BLAST_RADIUS=1` (5 tools) — the budget test only asserts the flag-off number, since that's the "cheap at session start" case; the flag is opt-in and not part of the default budget.
  > **Superseded 2026-09-27:** the user raised the budget to 7000 chars because stripping every tool/param description cost model accuracy for only ~300 tokens of savings — see "Budget raised to 7000 chars to keep tool/param descriptions" below.
- **2026-09-27 — Budget raised to 7000 chars (flag off) to keep tool/param descriptions; `title` stays dropped.** Following the prior entry, the user decided 5000 chars traded too much model guidance for too little space and raised `MAX_TOOLS_LIST_CHARS` in `mcp/test/tools-list.test.ts` to 7000 (plan updated at `docs/plans/mcp-server-plan.md` Phase 3 step 2). Restored verb-first, ≤300-char tool descriptions (what it does, what it returns, what to call next) and short `.describe()` on the key params only (`repo`, `agentId`, `runId`, `prNumber`, `minSeverity`, `cursor`, `response_format`), plus one output-schema describe for severity meaning (`findings[].severity`: `'CRITICAL > WARNING > SUGGESTION'`). `title` stayed dropped — the budget didn't need it back, and no test asserts it. Measured 2026-09-27: **5813 chars (~1454 tokens at chars/4) with the flag off**, well within 7000; **6423 chars (~1606 tokens)** with `DEVDIGEST_MCP_ENABLE_BLAST_RADIUS=1` (5 tools).

## Gotchas & recurring errors

- **2026-09-27 — `apiErrorResult`'s kind-specific hint duplicates any hint already baked into the `ApiError` message.** `src/format/result.ts#apiErrorResult` appends one hint per `ApiError.kind` (e.g. "Start the API with ./scripts/dev.sh, then retry." for `unreachable`). `src/api/http.ts` must **not** also put that hint text in the `ApiError`'s own `message` — the tool's `isError` text ends up with the sentence twice. Keep `ApiError` messages purely descriptive ("DevDigest API is not reachable at ...") and let `apiErrorResult` be the only place that adds an actionable hint.
- **2026-09-27 — `@modelcontextprotocol/inspector`'s `--cli` mode (v1 via `npx @modelcontextprotocol/inspector`, and v2 via `@latest`) would not accept `<command> --tsconfig ... src/index.ts --method tools/list` in this environment** — target-then-flags order fed `--method tools/list` to the spawned `tsx` process instead of the inspector, and flags-then-target order (`--method tools/list -- <command>...`) reported "Method is required" / "No servers found in config file". `@latest` (v2, package `@modelcontextprotocol/inspector@2.8.0`) also requires Node ≥22.19; this environment has 22.17. Verified the server correctly instead with a ~60-line scripted newline-delimited JSON-RPC client over the child process's stdio (`initialize` → `notifications/initialized` → `tools/list` → `tools/call`), per `shared/stdio.js`'s framing (`JSON.stringify(message) + '\n'`, no `Content-Length` headers). `npm run inspect`'s web/TUI mode was not exercised.
- **2026-09-27 — `test/fakes.ts#FakeDevDigestApi.failWith` is checked by every port method, so it can't isolate a failure to one call in a multi-call tool flow.** `run_agent_on_pr` calls `resolveRepo()` (→ `api.listRepos()`) before `api.startRun()`; setting `api.failWith` to simulate a `startRun`-only error (e.g. `not_found` from a missing PR) also made the preceding `listRepos()` throw, so the tool never reached `startRun` and the test saw only `apiErrorResult`'s generic per-kind hint instead of `run-agent-on-pr.ts`'s extra `EXTRA_HINTS` text. Fixed by adding a second, method-scoped flag (`startRunFailWith`, checked only in `startRun`) rather than reusing `failWith`. When adding a new `DevDigestApi` port method that a tool calls *after* another port method in the same handler, give it (or reuse) a dedicated fail flag instead of the shared one. Evidence: `mcp/test/fakes.ts` (`startRunFailWith`), `mcp/test/tools.test.ts` "adds the not_found hint (list_agents / import the PR) on top of the generic one".
- **2026-09-27 — `@modelcontextprotocol/sdk@1.30.1`'s `tools/list` handler always emits `"$schema":"http://json-schema.org/draft-07/schema#"` on every input/outputSchema; `zod-to-json-schema` (used internally) has no option to suppress it.** Fixed by re-registering the `tools/list` method *after* every tool is added: `Protocol.setRequestHandler`'s own docstring says replacing a method's handler is safe ("this will replace any previous request handler for the same method"), so `mcp/src/tools/_register.ts#stripJsonSchemaMetaFromToolsList` reads the SDK's own already-installed handler out of the (unexported but plain, non-`#private`) `server.server._requestHandlers` map, calls it for the real work, and strips `$schema`/`$defs`/`$ref` from the result recursively before returning it. `tools/call`'s output validation reads `tool.outputSchema` (the zod schema) directly, never this JSON Schema projection, so `structuredContent` validation is unaffected — confirmed via `mcp/test/tools.test.ts`'s existing `structuredContent` assertions still passing. Verified with a real stdio JSON-RPC session (not just `InMemoryTransport`): `tools/list` response contains no `$schema` substring with or without `DEVDIGEST_MCP_ENABLE_BLAST_RADIUS=1`.
