## Summary

Reviewers often open someone else's PR with no context. DevDigest already computes Intent, Smart Diff roles and Blast radius, but nothing tells the reviewer what is risky or where to start reading. PR Brief adds one block to the Overview tab. When the user asks for it, DevDigest makes **one** bounded model call over facts it has already computed. The model **never sees diff code**. It returns a summary of what the PR changes and why, **Risk areas**, and **Review focus**.

Every cited file is checked against the PR and its blast radius. Invented files are dropped. A focus line (and, since revision 2, a risk line) that falls outside the changed code is moved to the nearest changed range. The brief is stored with the commit SHA it describes, is shown instantly on reload, and is marked outdated when the PR head moves.

**Revision 2** brings the shipped block in line with the Lab 05 design. Overview shows one PR Brief block: a banner that pairs the brief's summary with the latest review's verdict and score, a two-column area (`Intent + Risk areas` | `Blast radius`), and a full-width Review focus block. Risks become expandable pills with an icon per kind and an optional line. A brief target whose file is not in the diff no longer leaves Overview. Arrival on Files changed is clearer: the target card gets an accent border and the target line gets a one-time highlight. The server side changes only in two small ways: the brief's instructions list the allowed risk kinds, and a risk may carry an optional, grounded line. Stored briefs from revision 1 stay readable.

## Goals / Non-goals

**Goals**
- A PR Brief block on Overview with a "Generate brief" action. The block shows a summary of what the PR changes and why, Risk areas and Review focus, together with the existing Intent and Blast radius blocks.
- One model invocation per generation, using the `risk_brief` model setting, over precomputed facts only, within **8 000 tokens** of input.
- No invented files. Every cited file is a changed file or a blast caller file, and every focus line or risk line shown lies in a changed line range or on a caller line of its file.
- A stored brief tied to its head SHA. Reload shows it without regenerating. When the head moves, the brief is marked outdated and offers a refresh action.
- Click-through from a Review focus item to that file and line on Files changed, and from a risk to its file (and line, when it has one).
- Generation still succeeds when facts are missing, and the brief says which ones.
- Included P3 items: a skeleton, labels from the `brief` catalog, "File not in this PR's diff", and risk click-through.
- **Revision 2:**
  - the design's layout: one block made of a banner, a two-column area and a full-width Review focus block, with each heading shown once;
  - the verdict banner (homework P3), which combines the brief's summary with the latest review's verdict, findings badge and PR score;
  - expandable risk pills (homework P3), with an icon per `kind` and severity shown by colour and by text;
  - an optional grounded line on each risk;
  - the design's empty, skeleton and refresh states;
  - the "not in diff" notice on Overview, and the arrival presentation on Files changed.

**Non-goals:**
- sending diff hunk bodies, or any file contents other than specs, to the model;
- prior-PR history, including the design's "Prior PRs touching these files" accordion (G16);
- automatic generation, streaming, or editing the output;
- an e2e browser flow;
- changes to LLM provider retries, timeouts or adapters;
- new persistent storage, or a migration of stored briefs;
- changes to how Intent, Blast radius, Smart Diff, Project Context or reviews compute their results;
- adding the brief's cost to the PR list's COST column;
- *(revision 2)* Markdown in risk explanations: the design's "lightweight markdown" is dropped and explanations stay plain text (P-6);
- *(revision 2)* line ranges on risks: the design shows `file:12-18`, but a risk carries at most one line, for its first file reference;
- *(revision 2)* marking the banner's review verdict as outdated relative to the PR head or the brief (P-16);
- *(revision 2)* a layout for narrow or mobile viewports beyond what the page already does;
- *(revision 2)* changing the duration, position or look of any other notification in the app.

## Definitions

- **Brief**: the stored result of the latest successful generation for a PR. There is one per PR, and a new generation replaces it.
- **Changed files**: the PR's full list of changed paths at generation time. A renamed file is listed under its new path.
- **Changed line range**: the new-side (head) span of one hunk, taken from its range header only. `+c,d` covers lines `c … c+d−1`. A missing `d` means 1, and `d = 0` covers no line.
- **Blast caller locations**: the `(file, line)` pairs of every blast-radius caller at generation time, as the blast computation returns them. They are never re-filtered.
- **Grounded file**: a path that exactly equals a changed file or a blast caller file. The match is case-sensitive and repository-relative.
- **Grounded line** in file F: a line inside a changed line range of F, or equal to a blast caller line in F.
- **Snapping**: applies to a focus line, or *(revision 2)* a risk line, L in a grounded file F when L is not a grounded line in F.
  - If F has changed line ranges, L moves to the start line of the nearest range (smallest distance from L to the range; on a tie, the earlier range).
  - Otherwise, if F has blast caller lines, L moves to the nearest caller line (on a tie, the earlier one).
  - Otherwise L cannot be snapped. The focus item is dropped. A risk keeps its file references and loses only its line.
- **Risk line** *(revision 2)*: a head-side line number that a risk may have. It refers to the risk's first file reference. A risk without a line has `line` null (or, in a revision-1 record, no `line` at all) (R2-5).
- **Facts**: the intent, blast, diff statistics, PR title, description, linked issue and specs. Each fact gets a status in the brief (see Contracts). A stale intent is still sent, marked as stale.
- **Brief agent**: the agent of the most recently started run, of any status, on the PR's repository, among agents that still exist in the workspace.
- **Stale**: the brief's stored head SHA differs from the PR's current head SHA. If the current head SHA is unknown, the brief is not stale.
- **PR's diff files** *(revision 2)*: the list of the PR's changed files that Files changed renders.
- **Brief target** *(revision 2)*: a control in the brief that leads to Files changed. These are a Review focus row, a risk pill's main area, and a file link inside an expanded risk panel.
- **Verdict review** *(revision 2)*: the most recent of the PR's reviews that carries a verdict.

## User stories

- **US-1** As a reviewer opening a PR cold, I want a PR Brief block I can generate on demand, so that I get (and pay for) a briefing only when I want one.
- **US-2** As a reviewer, I want a summary of what the PR changes and why, with Risk areas and Review focus together with Intent and Blast radius, so that I know why the PR exists, what is risky, and where to start.
- **US-3** As a reviewer, I want every risk and focus item to point at a real file (and line) of this PR or its blast radius, so that I can trust it.
- **US-4** As a reviewer, I want to click a focus item or a risk and land on that file (and line) in Files changed, so that I can start reading right away.
- **US-5** As a reviewer, I want the brief to load instantly on reload, to be told when it is outdated, and to refresh it when I choose, so that I neither wait nor pay twice.
- **US-6** As a workspace owner, I want each generation to be one bounded call with no code, made with the model I configured, so that cost is predictable and PR code cannot steer the model.
- **US-7** As a reviewer of a PR with incomplete data, I want the brief to say which facts were missing, so that I can judge how far to rely on it.
- **US-8** As the course mentor, I want the spec, plan, cross-model note, verifier report and demo in the PR, so that the process can be audited.
- **US-9** *(revision 2)* As a reviewer, I want the latest review's verdict, findings and score shown next to the brief's summary, with a note on where each comes from, so that I see the agents' conclusion and the briefing in one place without mixing up their sources.

## Workflow

```mermaid
sequenceDiagram
  actor U as Reviewer
  participant C as Client
  participant S as Server (brief)
  participant R as Reviews (existing)
  participant F as Facts: PR + files, Intent, Blast, Project Context
  participant ST as Settings (risk_brief)
  participant L as LLM

  U->>C: open PR → Overview
  C->>S: get brief
  S-->>C: stored brief + stale flag, or none (no LLM, no recompute)
  C->>R: PR reviews (already read by the PR page)
  R-->>C: latest review with a verdict: verdict, score, findings
  C-->>U: banner (brief summary + review verdict) → [Intent + Risk areas | Blast] → Review focus → notes
  U->>C: Generate brief / Refresh
  C-->>U: skeleton (on refresh: banner stays, spinner replaces score)
  C->>S: generate brief
  S->>F: stats, hunk ranges, description, issue, head SHA; stored intent; blast; brief agent's docs
  S->>ST: provider + model
  S->>S: build input ≤ 8 000 tokens, untrusted blocks
  S->>L: ONE structured-output invocation (repair re-asks inside it)
  L-->>S: {summary, risks[] (each with line or null), review_focus[]}
  S->>S: validate → ground (drop files, snap focus + risk lines) → replace stored brief
  S-->>C: brief
  U->>C: activate a brief target
  alt file is among the PR's diff files
    C-->>U: ?tab=diff&file=…&line=… → file expanded, card accent border, line highlighted once
  else file not in the diff
    C-->>U: stay on Overview, notice "File not in this PR's diff: {file}" (2.6 s)
  end
```

**Ownership**
- **Brief server:** input assembly, the budget, the model call, validation, grounding (including risk lines), storage, staleness, the rate limit and logging.
- **Intent Layer:** the intent record. The brief only reads it.
- **Blast radius:** the callers. The brief consumes them as given.
- **Project Context:** attachment resolution and the untrusted rendering of documents.
- **Settings:** the `risk_brief` model.
- **Reviews** *(revision 2)*: the verdict, the PR score and the findings shown in the banner. The brief neither stores nor changes them, and the brief server does not read them.
- **`@devdigest/shared`:** all shapes, identical in both copies.
- **Client:** presentation and navigation only. It never re-grounds, counts tokens or computes staleness. It picks the verdict review from the reviews data it already has.

## Acceptance criteria

### Overview block (US-1, US-2, US-5, US-7, US-9)

- **AC-1** (US-1, US-2) *(revised r2)*: When the user opens the Overview tab of a pull request, the client shall show exactly one PR Brief block, headed "PR Brief". The block contains the existing Intent and Blast radius blocks plus either the stored brief or, while no brief is stored, the empty state of AC-69 with its "Generate brief" action.
- **AC-3** (US-1, US-5, US-6): The system shall generate a brief only, and always, when the user triggers "Generate brief" or the refresh action, whether or not a stored brief exists or is stale. It shall never generate one on page open, on a review run, or on a new commit.
- **AC-4** (US-1) *(revised r2)*: While the pull request's identifier is unresolved, or the brief is loading and no brief is shown, or a generation is in flight while no brief is stored, the PR Brief block shall show a skeleton in place of its content and shall disable the generate and refresh actions. ### Facts and specs (US-7)

- **AC-20** (US-7): If any fact is missing or degraded at generation time, then the server shall still generate the brief and record each fact's status in it (Contracts `facts`). This includes a stale intent, which is still sent but marked as stale.
- **AC-22** (US-7): When generating, the server shall use as specs the documents that Project Context resolves for the brief agent on the PR's repository: the agent's direct attachments plus those of skills enabled both for that agent and globally. Project Context's de-duplication, default-branch and skip rules apply. The server shall record the brief agent and the spec paths that were included and omitted.

### Generation and model input (US-6)

- **AC-26** (US-6): When the user triggers a generation, the server shall make exactly one structured-output model invocation for it. The helper's JSON-repair re-asks are allowed within that invocation and are counted as `attempts`.
- **AC-27** (US-6): The server shall use the provider and model resolved for the workspace's `risk_brief` setting, falling back to that feature's registry default, and shall record both in the brief.
- **AC-28** (US-6): The server shall build the model input only from the inputs listed in Provenance. The input shall contain no diff hunk body line (added, removed or context) and no file content other than the resolved spec documents.
- **AC-30** (US-6): The model input of the request as first sent shall not exceed 8 000 tokens. This counts the system and user messages with the server's tokenizer. Each source is capped at its Provenance share, any remaining overflow is removed in the fixed reduction order, and each reduction is recorded in the brief.
- **AC-34** (US-6): If the input cannot fit within 8 000 tokens after every reduction, then the server shall fail the generation with a budget error, make no model invocation, and leave the stored brief unchanged.
- **AC-35** (US-6): The server shall place every untrusted input (see Provenance) in its own delimited untrusted block that its content cannot close early. Outside those blocks, the server shall instruct the model to treat their content as data only.
- **AC-73** (US-3, US-6) *(new r2, G10-B, G11; amended by R2-5)*: The server's brief instructions shall:
  - ask the model to set each risk's `kind` to one of `security`, `db_migration`, `breaking_api`, `perf`, `deps` or `other`;
  - ask the model to give each risk's `line` as a head-side line of the risk's first file reference, or null when no single line applies, while `file_refs` stay bare paths without line numbers.

  The output contract shall still accept any string as `kind`, and shall accept null as a risk's `line` (R2-5).

### Validation, grounding, storage (US-3, US-5, US-6)

- **AC-36** (US-3, US-6): The server shall validate the model's response against the shared output contract before grounding. If the response is still invalid after the allowed attempts, then the server shall fail the generation and leave the stored brief unchanged.
- **AC-37** (US-3) *(revised r2)*: The server shall ground against the full set of changed files, changed line ranges and blast caller locations at generation time, not only the subset sent to the model. Grounding shall:
  - remove every risk file reference that is not a grounded file, and drop every risk left without references;
  - drop every focus item whose file is not grounded;
  - snap the line of every focus item whose file is grounded but whose line is not, dropping the item only when it cannot be snapped (see Definitions);
  - keep a risk's `line` only while the first file reference the model returned survives grounding (P-7). Such a line is snapped when it is not a grounded line in that file. Only the line is dropped, and the risk is kept, when the line cannot be snapped or when its reference was removed;
  - store the result with its removal counts, its focus-line snap count and its risk-line snap and drop counts, even when nothing remains. A line of a risk that is dropped entirely is not counted as a dropped risk line.
- **AC-41** (US-3, US-6) *(revised r2; amended by R2-5)*: The shared brief contracts shall define:
  - `summary`;
  - `review_focus` items `{file, line, reason}`;
  - risk items with a `line` placed directly after `file_refs`. In the model output this `line` is nullable, not optional (null = no line). In the stored record it may be missing or null (R2-5);
  - the risk-line grounding counters as optional fields of the stored record.

  The two vendored copies of the brief contracts shall be identical.
- **AC-42** (US-5): When a generation succeeds, the server shall replace the PR's stored brief with the grounded result. The stored brief shall include the head SHA all inputs were read at, the generation time, the facts, the reductions and the usage.
- **AC-43** (US-5): When the Overview tab is opened or reloaded for a PR that has a stored brief, the system shall show that brief with its stale flag. It shall make no generation request, model invocation, intent derivation or blast computation.
- **AC-46** (US-6): If a generation is requested for a PR with no known changed files, or exceeds 10 requests per minute per client, then the server shall reject it with a validation error or a rate-limit error respectively. It shall make no model invocation and leave the stored brief unchanged.
- **AC-49** (US-3, US-6): If the pull request does not exist or belongs to another workspace, then reading and generating the brief shall respond not-found and change nothing.
- **AC-51** (US-6) *(revised r2)*: When a generation finishes, the server shall write exactly one structured log line. On success, it shall also store the same usage in the brief. The usage covers:
  - outcome, provider, model and `attempts`;
  - cumulative provider-reported input and output tokens, and cost (or null);
  - server-counted input tokens, in total and per source;
  - the reductions, the grounding removal counts, the focus-line snap count, and the risk-line snap and drop counts.

  The log line shall never contain description, issue, spec or model-output text.
- **AC-74** (US-3, US-5) *(new r2, G11; amended by R2-5)*: When a brief stored before revision 2 is read (its risks have no `line` and its grounding has no risk-line counters), the server shall return it without error and without rewriting it. The client shall render it with no risk lines and with the missing counters treated as zero. A stored risk whose `line` is null shall be read and rendered the same way as one without a `line`.

## Non-functional requirements

- **NFR-1 Security (untrusted input).**
  - All author-controlled text reaches the model only inside untrusted blocks, under an injection guard (AC-35). No code is sent (AC-28).
  - Model output is treated as untrusted. Ungrounded files are dropped, and focus and risk lines are snapped into the PR's changed ranges or caller lines, or dropped (AC-37). Output is rendered as plain text, explanations included (AC-13, AC-72). Navigation targets come only from grounded paths and are URL-encoded (AC-52, AC-54, AC-76).
  - *(revision 2)* `kind` only selects an icon from the fixed map (AC-71). It is never shown as markup or used to build a style or a link.
  - Specs come from the default branch, so a PR cannot change the specs it is briefed against.
- **NFR-2 Data handling.** Logs carry identifiers, counts, tokens, costs and reasons only (AC-51). The brief holds no secrets. Keys are read only through the existing secrets provider.
- **NFR-3 Tenancy.** Every operation is scoped to the workspace. A cross-workspace request gets not-found (AC-49). *(revision 2)* The banner shows only reviews of the same PR that the page already reads.
- **NFR-4 Cost.**
  - One model invocation per generation (AC-26), and none on read (AC-43). Nothing is generated automatically (AC-3), and generation is rate-limited (AC-46).
  - Initial input is at most 8 000 tokens (AC-30), and output at most 1 500 tokens. *(revision 2)* The kind list and the risk-line rule count toward the system instructions inside the same 8 000 budget. The output cap does not change.
  - A repair re-ask resends the input plus the invalid output, so it shows up in `attempts` and in the cumulative tokens (AC-51). Provider transport retries are unchanged and are not counted.
  - *(revision 2)* Showing the verdict adds no model invocation and no new API endpoint (AC-65).
- **NFR-5 Performance.** Reading a brief: p95 ≤ 300 ms on a local stack (AC-43). Model timeout: 60 s. Work outside the model call: ≤ 3 s on an indexed repository. *(revision 2)* The not-in-diff notice disappears 2.6 s after it appears (AC-76). The arrival line highlight is gone within 2 s (AC-77).
- **NFR-6 Accessibility.**
  - Severity is never conveyed by colour alone (AC-13).
  - Focus items, risk pills and risk file links can be activated from the keyboard, with accessible names that include `file` (and `:line`) (AC-13, AC-52, AC-75).
  - The skeleton and the result are announced in a polite live region.
  - "Outdated" is shown as text (AC-45).
  - *(revision 2)* Further requirements:
    - the refresh icon button has an accessible name (AC-45);
    - the banner hint can be reached by keyboard and is exposed to assistive technology (AC-67);
    - the risk expand control exposes its expanded state (AC-72);
    - the "▸" marker is decorative (AC-75);
    - the not-in-diff notice is announced politely (AC-76);
    - reduced motion is respected for the arrival scroll and highlight (AC-78).
- **NFR-7 i18n.** All strings introduced by the PR Brief block come from the `brief` namespace. The verdict banner's existing labels may keep their namespace (AC-10). Existing keys are reused where they fit, new keys go inside the existing nested objects, and there are no duplicate top-level keys.
- **NFR-8 Compatibility.**
  - No new storage and no migration. Briefs stored before revision 2 stay readable and render (AC-74).
  - The Intent and Blast blocks compute and behave as before. The exceptions are the "Derive intent" label (AC-9), Intent's empty-state and error texts (AC-70), and their placement in the two-column area (AC-63).
  - Files changed, and every other diff view, behaves as before when no target is given.
  - Other notifications in the app keep their behaviour.

## Edge cases & errors

Missing or degraded facts (generation always proceeds):
- **EC-1** No intent → recorded as `missing` (AC-20, AC-16). The Intent block shows its own "No intent yet" empty state with "Derive intent" (AC-9, AC-70).
- **EC-2** Stale intent → still sent, and recorded as `stale` (AC-20).
- **EC-3** Blast degraded or failing → recorded as `degraded` (with the reason) or `unavailable`. Grounding uses whatever exists (AC-20, AC-37).
- **EC-4** No linked issue → recorded as `none` (AC-20).
- **EC-5** Empty or template-only description → recorded as `empty` (AC-20).
- **EC-6** No run on the repository, the last run's agent deleted, or no attachments → "no specs attached". Deleted agents are skipped when picking the brief agent (AC-20, AC-22).
- **EC-7** Clone unavailable → specs recorded as `unavailable` (AC-20).

Budget:
- **EC-8** A spec larger than the remaining specs share → that document is cut at its tail with its delimiter intact. Later documents are omitted, and the omission is recorded (AC-22, AC-30).
- **EC-9** A very large PR → the file list is cut from the tail, and the cut is recorded. Grounding still uses the full lists (AC-30, AC-37).
- **EC-10** The fixed parts alone exceed 8 000 tokens → budget error, and no model call (AC-34).
- **EC-31** Provider and server token counts differ → the budget is enforced on the server count. Both counts are recorded (AC-30, AC-51).

Grounding and model output:
- **EC-11** An invented, absolute, out-of-repository or `path:line`-suffixed reference → not a grounded file, so it is removed (AC-37). This still holds in revision 2: a risk line goes in its own field, never inside `file_refs` (AC-73).
- **EC-12** A focus line in a grounded file that lies outside every changed range and is not a caller line → kept, and snapped to the start of the nearest range (on a tie, the earlier range). A deleted file has no new-side range, so its focus item snaps to the nearest caller line in that file, or is dropped if there is none (AC-37).
- **EC-13** A binary or patch-less file → it has no ranges. Risks may still cite it. Its focus items snap to the nearest caller line in that file, or are dropped if there is none (AC-37).
- **EC-14** Everything is ungrounded → empty sections plus the removal note, not an error (AC-37, AC-16).
- **EC-15** Malformed or over-limit output (more than 6 risks or 8 focus items, a summary over 600 characters, or a risk `line` that is neither null nor a positive integer) → repaired within the attempts. If it still fails, the generation fails and the old brief remains (AC-26, AC-36, AC-8).
- **EC-16** Provider error, timeout, missing key, or unknown `risk_brief` model → an error with retry. The old brief is kept, and the failure is logged (AC-8, AC-51).
- **EC-17** A prompt injection in the description, issue or a spec → treated as data. Any invented path it produces is dropped (AC-35, AC-37).
- **EC-18** A path or symbol name crafted to break a delimiter → it cannot close its block (AC-35).
- **EC-33** *(r2)* A risk line outside every changed range of its first reference, and not a caller line → snapped like a focus line (AC-37).
- **EC-34** *(r2)* A risk line whose first reference has no changed range and no caller line (for example a binary file) → the line is dropped, the risk is kept, and a dropped risk line is counted (AC-37).
- **EC-35** *(r2)* A risk line whose first reference is removed by grounding while other references survive → the line is dropped (P-7). The pill shows the new first reference without a line (AC-37, AC-13).
- **EC-36** *(r2)* A risk `kind` outside the list (for example `api-contract` in a brief stored before revision 2, or `Security`) → AlertTriangle icon, and the brief still renders (AC-71).
- **EC-51** *(r2, R2-5)* The model has no single line for a risk → it returns `line: null`, which is valid output. The risk is stored without a line, and nothing is counted as a snapped or dropped risk line (AC-37, AC-41, AC-73).

Staleness and concurrency:
- **EC-19** A new commit after generation → "outdated", with no automatic regeneration (AC-45).
- **EC-20** The head moves during a generation → the SHA the inputs were read at is stored, so the brief is immediately stale (AC-42, AC-45).
- **EC-21** Two tabs generate at the same time → both call the model, and whichever finishes last is stored. Within one tab, the actions are disabled while a request is in flight (AC-4, AC-68, AC-42).
- **EC-24** Current head SHA unknown → not stale (Definitions, AC-45).
- **EC-25** Intent, specs, description or the model setting change without a new commit → not stale. The user refreshes manually (AC-3, AC-45).
- **EC-37** *(r2)* A brief stored before revision 2 → read and rendered without error. It has no risk lines, and the missing counters count as zero. It is not rewritten until the next generation. A stored risk `line` of null is treated the same as a missing one (AC-74, R2-5).

Rejected requests:
- **EC-22** Rate limit exceeded → rate-limit error, and no model call (AC-46).
- **EC-23** No known changed files (unsynced or empty PR) → validation error, and no model call (AC-46).
- **EC-30** Cross-workspace PR id → not-found (AC-49).

Banner (revision 2):
- **EC-38** The newest review has no verdict but an older one does → the older one is the verdict review (Definitions, AC-65).
- **EC-39** The PR has no review, or its reviews are still loading or failed to load → banner without verdict, badge or score, and no error in the brief block (AC-66).
- **EC-40** The verdict review has a verdict but no score → verdict and badge, no score. During a refresh, the spinner takes the score's place (AC-66, AC-68).
- **EC-41** The verdict review describes an older commit than the brief → shown as is. The hint names its source (P-16, AC-67).
- **EC-42** The brief's cost is unknown (`cost_usd` null) → "—" in place of the cost (AC-65).
- **EC-43** A refresh fails → the banner and the saved brief come back, with the error row directly below the banner (AC-8, AC-68).

Client and navigation:
- **EC-26** *(revised r2)* Activating a brief target whose file is only in the blast radius → stay on Overview and show the notice (AC-76).
- **EC-27** The target file is in a collapsed group, or is collapsed itself → it is expanded (AC-52).
- **EC-28** A `file` address parameter that matches nothing or contains odd characters → the not-in-diff note in Files changed, and nothing is fetched (AC-54).
- **EC-29** PR identifier still resolving → the skeleton, then the correct state, never an endless skeleton (AC-4).
- **EC-32** The focus or risk line is not rendered in the diff (for example, a caller line outside the hunks) → scroll to the file header, with no error (AC-52).
- **EC-44** *(r2)* Not-in-diff targets activated several times in a row → one notice at a time, and its 2.6 s restart (P-11, AC-76).
- **EC-45** *(r2)* A second risk pill expanded while one is open → the first closes. Activating the open pill's control closes it (AC-72).
- **EC-46** *(r2)* The same target is activated again after Back → the accent border and the one-time line highlight show again (AC-77).
- **EC-47** *(r2)* Reduced motion requested → instant scroll and a static highlight (AC-78).
- **EC-48** *(r2)* A very long focus path → cut visually, complete in its tooltip and accessible name, with no horizontal page scroll (AC-75).
- **EC-49** *(r2, amended by R2-6)* Intent is loading, empty or failed while a brief is shown → the left card shows only Intent's own state (skeleton, "No intent yet" empty state, or error with retry), with no "Intent" heading, above Risk areas. The brief is unaffected (AC-63, AC-64, AC-70, NFR-8).
- **EC-50** *(r2)* A risk pill whose first reference is a blast-only file → activating it shows the notice (AC-76). Panel links to other references that are in the diff still navigate (AC-52).

## Provenance of model inputs

The budget unit is **tokens**, counted with the server's tokenizer (the one Project Context uses) over the exact text sent, delimiters included. The limit is **8 000** for the system and user messages of the request as first sent. Shares are ceilings, not reservations. The system instructions have no share of their own but count toward the total, including, since revision 2, the kind list and the risk-line rule. Overflow is removed in the order given in the "Global order" column.

| # | Input | Source | Trust | Share | Within-share reduction | Global order |
|---|---|---|---|---|---|---|
| 1 | System instructions (role, injection guard, output and grounding rules, allowed risk kinds, risk-line rule) | brief feature | trusted | — | never | — |
| 2 | Intent: statement, in/out of scope, change type, confidence, stale marker | Intent Layer record | **untrusted** (model-derived from author text) | ≤ 600 | text tail cut | — |
| 3 | Blast summary + caller locations (`file:line`, symbol) | blast computation (no LLM) | counts trusted; **paths, symbols untrusted** | ≤ 1 500 | caller-list tail | — |
| 4 | Diff stats: path, +/−, Smart Diff role, changed line ranges | PR files; Smart Diff; hunk headers (numbers only) | numbers, roles, ranges trusted; **paths untrusted** | ≤ 2 000 | file-list tail | 2nd |
| 5 | PR title, description, linked issue title + body | PR record / GitHub, when DevDigest has it | **untrusted** | ≤ 1 500 | text tail cut | 3rd |
| 6 | Spec documents (path + text) | Project Context, default branch | **untrusted** | ≤ 2 400 | in prompt order; the document that crosses the limit is cut at its tail, later ones omitted | 1st |
| — | **Never sent:** hunk body lines, other file contents, commits, findings, review verdicts or scores, prior-PR history, secrets | — | — | 0 | — | — |

## Contracts

These are behaviour-level contracts. Schema names, module placement, and any error status code not listed here are the planner's choice, consistent with the server's error handler. Shapes go into `@devdigest/shared` first, as a targeted port to both copies. Names marked *(proposed)* may be renamed. All other names are fixed by the homework or by existing contracts.

**Model output** (validated before grounding):
- `summary`: non-empty, at most 600 characters, stating what the PR changes and why.
- `risks[]`: at most 6 items, each `{file_refs (≥ 1 path), line (integer|null), explanation, title, kind, severity: high|medium|low}`.
  - *(revision 2, R2-5)* `line`: **nullable, not optional**. It is either an integer ≥ 1 on the head side, referring to `file_refs[0]`, or null when the risk has no line. The model output is strict structured output, where an optional field would become required and non-null and the model would have to make up a line. The same rule (nullable, never optional) applies to any other new model-output field the model may leave empty.
  - *(revision 2)* `kind`: any string is accepted. The instructions ask for one of `security`, `db_migration`, `breaking_api`, `perf`, `deps`, `other` (AC-73).
- `review_focus[]`: at most 8 items, in reading order, each `{file, line (integer ≥ 1, head side), reason}`.
- The output is capped at 1 500 tokens.
- Field order goes from observed to classified (server INSIGHTS): `file_refs`, then `line`, then `explanation` come before `kind` and `severity`, and `file` and `line` come before `reason`.

**Stored brief** (one per PR, inside the existing per-PR brief record):
- `summary`, plus `risks[]` and `review_focus[]` after grounding. Snapped focus items carry the snapped line. *(revision 2, R2-5)* A risk has a non-null `line` only when its line was kept or snapped (AC-37). Otherwise its `line` is null, or missing in a revision-1 record. Readers treat missing and null the same.
- `head_sha`, `generated_at`, `provider` and `model`.
- `usage` *(proposed)*: `{tokens_in, tokens_out, cost_usd|null, attempts, input_tokens_total, input_tokens_by_source}`.
- `reductions[]` *(proposed)*: `{source, tokens_before, tokens_after, items_omitted}`.
- `facts` *(proposed)*:
  - `intent`: `present|stale|missing`
  - `blast`: `present|degraded(+reason)|unavailable`
  - `linked_issue`: `present|none`
  - `description`: `present|empty`
  - `specs`: `{status: included|none_attached|no_agent|unavailable, agent: {id,name}|null, included_paths[], omitted_paths[]}`
- `grounding`: `{risks_dropped, risk_refs_removed, focus_dropped, focus_lines_snapped, risk_lines_snapped?, risk_lines_dropped?}`. The user fixed the name `focus_lines_snapped`; the other names are *(proposed)*. *(revision 2)* The two risk-line counters are optional. A record without them means zero.
- **Backward compatibility** *(revision 2)*: a record written by revision 1 (no risk `line`, no risk-line counters) must pass the same read contract unchanged. So must a record whose risk `line` is null (R2-5). Reading never rewrites a record (AC-74).
- The existing `PrBrief {intent, blast, risks, history}` does not have to embed intent, blast or history. The planner may extend it or add a sibling shape, as long as AC-41 holds.

**API**
- `GET /pulls/:id/brief` returns `{brief | null, stale}`.
- `POST /pulls/:id/brief` takes no options, always regenerates, and returns the new brief with `stale: false`.
- Revision 2 changes no endpoint. The responses carry only the new fields above: a risk `line` that is null or missing when absent, and the optional counters.
- POST errors all leave the stored brief unchanged:
  - not-found (AC-49);
  - 422 when the PR has no changed files (AC-46);
  - 429 when rate-limited (AC-46);
  - a budget error (AC-34);
  - an upstream model failure (AC-36, EC-16).
